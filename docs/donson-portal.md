# Donson student portal and operator workspace

The Donson fork keeps the existing school protocol and check-in safeguards, adds a school-verified student portal at `/`, and places the operator UI at `/admin` on a separate private listener (see [private administration](private-admin.md)). The public student listener returns 404 for operator routes and APIs.

Students sign in with their student ID and school password. First use opens an isolated server browser inside the portal; the student completes school MFA/CAPTCHA there, and school-issued browser trust is collected without installation or copying. The manual fingerprint fallback is available only when the helper is disabled. Verification forces fresh school password authentication with an empty Cookie jar; verification itself never submits a check-in. MFA and CAPTCHA are completed by the student in the displayed school page.

After verification, encrypted school credentials and Cookies are bound to a single ordinary user. The password is also hashed with Argon2 for local sign-in for up to 24 hours after school verification. Expiry, changed credentials, or changed browser trust trigger school verification again. Local sessions expire after 12 hours or 30 minutes idle. Password changes detected on re-verification revoke earlier local sessions. An unobserved school password change is not detected until re-verification.

An existing operator-owned school account can be transferred only after successful verification of its exact student ID. Its ID, job history, location and schedule are preserved. Ordinary users can access only their own account and cannot bind a second account, modify verified identity, manage other users, or change a separate site password. Administrators can pause users/accounts, edit configuration and review global records; APIs do not return passwords or trusted-browser fingerprint values.

Set `MOON_ENABLE_PORTAL=1` and `MOON_ALLOW_REGISTRATION=0`. The legacy username/password registration API stays disabled; student onboarding happens only through school verification. Both interfaces remain same-origin with Host, Origin and CSRF enforcement. `MOON_TRUSTED_PROXY_CIDRS` must contain only the actual local reverse-proxy peer address; untrusted peers cannot override their rate-limit IP with CF-Connecting-IP.

`MOON_STUDENT_ID_PREFIX` defines the default open cohort (that prefix plus exactly two ASCII digits). In `/admin/users`, administrators can add or revoke individual school-ID exceptions under “学号登录授权”. Authorization only opens access to school sign-in; it does not create an account or satisfy MFA. Exceptions are encrypted with the existing vault key and persist across restarts. Only administrators can read or change them, write requests require Origin/CSRF checks, and audit targets contain keyed digests rather than school IDs. Revocation invalidates out-of-cohort sessions and prevents new or in-progress verification from binding an identity; stored users and history remain intact. Deleting a test user does not implicitly remove its separate login authorization.

The new interface uses React, Radix Primitives and Sonner. Radix manages modal focus, keyboard interaction, menus and switches. One Sonner Toaster is mounted at the app root. The new interface permits inline style properties for component positioning while keeping scripts same-origin; inline scripts and third-party connections remain disallowed. Legacy pages retain their stricter style policy. All pages carry noindex/nofollow.

Frontend build: `cd frontend && pnpm install --frozen-lockfile && pnpm build`. Built assets live in moonuestc/web_static/ui and are included by the Python Dockerfile. The runtime remains Python-only; no Node or GPU service is required on the Jetson. License texts for bundled UI packages are under third_party/ui.

The upstream SHA256SUMS and validation snapshots describe upstream 0.5.1, not this fork. Verify a Donson deployment against its own release manifest and deployment evidence. Do not publish private deployment artifacts, databases, backups or credentials.

Assisted verification preserves the actual school's DOM, CSS, modal structure and visibility inside a script-disabled sandbox. It no longer flattens controls into a substitute form or streams full-page screenshots. A keyed DOM patcher retains typing, focus and scroll while reflecting school-side updates. Only backend-isolated school scripts run; owner events reference exact nodes from the current document. Hidden tokens, primary credentials and executable markup are removed. Owner-bound static resource references preserve school styles/images/fonts without offering an arbitrary URL proxy; already-loaded QR resources are reused rather than requested again. Revision requests suppress unchanged HTML, with gzip for changed documents. This is a passive presentation of the backend school page, not direct access to the user's school-domain cookies. Ordinary `moon.donson.top` JavaScript cannot read `idas.uestc.edu.cn` cookies in the user's browser. MFA and trust choices remain the user's actions.

Interactive school verification uses a persisted local rolling guard: ten new flows per school identity in a rolling five-minute window. An assisted flow shares one private, account-bound, single-use permit with its final independent password check. A flow can send one initial browser password POST plus one fresh verification POST. Preparation cannot submit credentials before the separate begin command; startup failures and cancellations are refunded only when no password POST was sent. Unknown submission outcomes retain their permit. Cooldowns return an exact Retry-After header and JSON retry_after, displayed as a countdown. Earlier daily counters do not block interactive onboarding. The unattended runner retains its separate three-per-day password retry cap; historical daily counters remain intact.


First-use onboarding validates the primary school password before opening the school page. The helper returns a safe rejected/pending/challenge/verification status; a slow validation remains on the existing login form, and an invalid password returns an inline error. CAPTCHA before password validation remains an exception requiring the owner's input. School MFA controls and provider pages retain their original UI.

WeChat navigation permits only the exact official provider, static and polling hosts, with a school-domain redirect callback. Redirected provider documents are validated before enabling their QR/poll requests; child frames and provider popups remain inside the owner-bound helper. School names are observed from school MFA greetings, never the client or WeChat profile. A valid observed name is applied to the ordinary user's existing display_name only after independent school identity verification succeeds; missing/invalid names leave the current display unchanged. No name is recorded in audit text or diagnostic artifacts.


The student home page follows an explicit sequence: configure actual location/time, read-only school/location check, one confirmed manual submission, then optional automatic execution. A configuration edit invalidates the previous check indicator. Pending work disables duplicate actions; an uncertain submission offers a recheck and keeps its original durable claim. Mobile navigation includes text labels.

Deployment can restrict location choices with `MOON_ALLOWED_PRESETS=xuezhi_group2_amap,xuezhi_group5_amap` and execution to `MOON_RUN_WINDOW=21:06,23:24`. These are portal restrictions; the upstream CLI coordinate catalog remains available. A selectable preset does not override the account's school geofence. Existing locations are retained for review rather than silently replaced; unavailable ones must be changed before new execution.

Optional daily variation is configured as `variation: {minutes: 5, meters: 5}` (each integer 0–5). A private random seed is stored inside the encrypted account payload. HMAC-derived daily values stay identical across polling, retries, independent processes and restarts. A time offset stays inside the portal interval and known school window; live school time is checked again before posting. A radius uses a uniform disk around the selected GCJ-02 point, and the complete disk must fit one school fence. Actual submitted coordinates are checked again; rejected locations are never snapped or replaced. Existing accounts default to zero variation until saved; new portal accounts with restricted locations default to 5/5 but require explicit location selection. No new automated schedule is enabled by deployment.

The helper uses one Chromium instance and at most two temporary isolated contexts for interactive school authentication. Routine jobs use saved school Cookies/HTTP, not browser sessions. New students automatically get a distinct random device profile; successful final verification stores it encrypted so returning students can reuse their existing trust. A cancelled or failed first-use flow does not bind a profile. Older accounts use their prior private HMAC-derived profile as a fallback. The login page has no new-device/testing checkbox. The school calculates its own fingerprint and decides whether MFA is required.


School-account names for ordinary users follow their verified display name. The one-time migration synchronizes existing labels without changing account credentials or schedules; operator-held accounts retain their operator labels until assigned to a student. Queue position is shown during pending jobs. A dedicated worker processes queued HTTP tasks one at a time with a 20-second minimum inter-task gap; the browser's two-context limit applies only to interactive verification. See private-admin.md for the queue boundary and deadline behavior.


Reserved scheduling supersedes shared nominal times in the portal. Every bound account receives a unique primary dispatch window in the first half of a minute, normally between 21:06 and 23:19. The stored run_at is now a preference, not a promise to submit at that exact minute. Changing it chooses a free window near the preference. The compatibility variation.minutes field enables a stable 0–19-second daily offset inside that account's owned window. CLI accounts without a portal execution window retain the original minute-variation behavior. Retry dispatches use unique second-half minute windows at least 120 seconds later; the worker never starts a new submission after its reserved deadline. Slow school requests can still cause a retry or final failure rather than successful attendance.

A versioned hosting notice appears before sending school credentials. It lists password/Cookie/device-marker storage, student identity, location and scheduling data, purposes, operator access, pauses, deletion and backup limits. The login banner remains visible. Browser receipts are keyed to a hash of the student ID; account A's acknowledgment cannot silently authorize account B. The server records version/time only after identity validation or an authenticated CSRF-checked acceptance. Existing sessions without the current notice are prompted, and scheduled work waits for acceptance. No QQbot is included in this release.
