# Assisted school onboarding

New students can use a phone or desktop without an extension or developer tools. They enter student ID and school password in the portal, complete the school's challenge in a temporary isolated server browser when required, and the server collects the school-issued trusted-browser cookie. The original student/password are then independently verified by the existing school client before binding.

This does not read cookies from a visitor's local browser or bypass same-origin/HttpOnly restrictions. The school's MFA/CAPTCHA is completed by the owner. The browser trust cookie is a school authorization marker, not a freely generated device hash.

The portal's `/api/onboarding/*` routes require a short-lived, owner-bound HttpOnly cookie. Every write action also requires an onboarding CSRF value plus the normal Origin check. The owner sees the original sanitized school DOM and CSS in a script-disabled iframe. Primary credentials, hidden tokens, cookies, fingerprint values and private browser IDs are never serialized into that document. Editable verification inputs stay local while exact-node events are relayed to the isolated browser. There is no full-page image stream.

The browser service has no published host port, accepts a private service key, uses isolated non-persistent browser contexts, and destroys contexts after five minutes or cancellation. At most two contexts are allowed. File downloads, off-allowlist requests and school attendance submission requests are blocked. School-authorized WeChat popups/frames use exact official hosts and a school-bound callback. A context can perform at most one original password-login POST and must keep its original student ID. School slider/image challenges are presented before the school can check the password. A CAPTCHA failure may require restarting onboarding; the product never solves CAPTCHA automatically. Server credentials pending a decision remain only in memory and expire with the session.

Interactive authentication permits ten flows per student in a rolling five-minute window; a separate request guard allows thirty student requests per five minutes. Cancellation refunds only a proven zero-password-POST flow. The unattended runner's daily retry budget is separate. Deployment sets `MOON_STUDENT_ID_PREFIX=20241909060`, admitting that prefix plus two ASCII digits and individual exceptions added by administrators in `/admin/users`. Scope is enforced before school calls or cached login and again in the final binding transaction. The same scope applies to existing ordinary-user sessions; administrators use their independent login. Withdrawing authorization does not delete stored users or permit a pending verification to create one.

The helper's Chromium sandbox is unavailable under the restricted container runtime, so it runs in a dedicated read-only non-root container with dropped capabilities, no-new-privileges, no host mounts and resource limits. It must stay private on the application network. Its temporary Chromium profile/cache uses tmpfs. Do not expose its service port or remove its key check.

Build the helper from browser_assist/Dockerfile on ARM64. `compose.browser.yaml` adds the private browser service; set MOON_BROWSER_ASSIST_URL to the internal service address and use a long random MOON_BROWSER_ASSIST_KEY in a private environment file. The main app remains independent of Playwright dependencies.

An anonymous school-page render proves browser/network compatibility only. Synthetic OTP tests prove the UI/state machine and binding boundary. Actual school MFA, issuance of a trusted-browser cookie, and school acceptance of the resulting binding still require an owner-operated real-account acceptance run. Do not describe those as live-verified until completed.


First-use device handling is automatic. Unbound students get a random temporary device profile; successful final verification binds it to the encrypted account record. Returning students reuse saved local/school sessions and the stored device profile; only school-requested verification opens the helper again. No device-testing switch appears on the login or settings page. Cancellation keeps the existing account intact and never stores an unverified first-use profile.
